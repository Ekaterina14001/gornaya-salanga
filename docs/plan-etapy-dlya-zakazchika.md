# Горная Саланга — план работ по этапам

Документ для заказчика. Актуально на июль 2026.

---

## Почему этапов четыре, а не три

| Вопрос | Ответ |
|--------|--------|
| **Почему магазины не вместе с кассами?** | Это разные задачи: магазины — **как гость скачивает приложение**; кассы — **как начисляются бонусы на объекте**. |
| **Почему магазины после «продакшена», но до касс?** | Сначала включаем SMS, HTTPS и push и проверяем приложение на web/APK. Потом публикуем в Store, когда backend стабилен. Кассы подключаем последними — на пилотной точке, когда гости уже могут пользоваться приложением. |
| **Можно ли поменять порядок?** | Да: POS можно начать параллельно со Store, если интегратор касс готов раньше. Store без HTTPS и SMS не имеет смысла — поэтому этап 2 всегда первый после демо. |

## Этап 3. Публикация в Google Play и App Store

**Цель:** гости скачивают приложение из официальных магазинов; не нужна ручная установка APK и не нужно объяснять «как открыть сайт в Safari».

**Статус: не начат**

> **Почему отдельный этап, а не вместе с кассами (этап 4)?**  
> Магазины — про **дистрибуцию** (скачать, обновления, отзывы). Кассы — про **бизнес-процесс на объекте**. Их делают разные подрядчики (мы + интегратор Shelter/r_keeper). Логично сначала стабилизировать backend (этап 2), опубликовать приложение (этап 3), затем подключать кассы на пилотной точке (этап 4).

## Этап 4. Интеграция с кассами (POS)

**Цель:** бонусы начисляются и списываются на реальных кассах без ручного ввода.

**Статус: не начат** (API для касс заложен в этапе 1)

### Состав работ

| Блок | Работы |
|------|--------|
| **API (готово)** | earn/spend, QR, API-ключи, логи — доработка по требованиям интегратора |
| **Shelter** | Совместная работа с интегратором |
| **Bars / r_keeper** | По необходимости, отдельные подэтапы |
| **Сценарии** | % от чека, списание бонусов; **начисление по отгрузке**, отмена и сторно при возврате |
| **Пилот** | 1–2 точки продаж на курорте |
| **Документация** | Инструкция для кассиров |
| **Отчёты** | Сверка транзакций (при необходимости) |

### Нужно от заказчика

- Контакты интеграторов касс
- Доступ к тестовой/боевой кассе
- Регламент бонусной программы
- Кассиры и IT на объекте при приёмке

### Результат этапа 4

Гость показывает QR → касса **резервирует** начисление при оплате → бонусы **зачисляются при отгрузке** → при возврате — автоматическая отмена или списание.

**Срок:** 6–12 недель (зависит от интеграторов)

## Новые требования заказчика (июль 2026)

### 1. Бонусы по отгрузке, а не по оплате

**Суть:** после оплаты клиент может оформить возврат — бонусы нельзя начислять сразу на кассе.

**Как работает сейчас (демо):** касса вызывает `/api/bonus/earn` → бонусы сразу на счёте.

**Как нужно заказчику:**

| Шаг | Событие на кассе / в учёте | Что делает система |
|-----|----------------------------|-------------------|
| 1 | **Оплата** (чек пробит) | Создаётся операция со статусом **«ожидает отгрузки»** — баланс гостя **не меняется** |
| 2 | **Отгрузка** (товар/услуга выдана) | Статус → **«начислено»**, бонусы зачисляются на счёт |
| 3 | **Возврат до отгрузки** | Операция **отменяется**, бонусов не было — ничего не списываем |
| 4 | **Возврат после отгрузки** | Создаётся **сторно** (списание ранее начисленных бонусов) |

**В приложении гость видит:**
- доступный баланс (только подтверждённые бонусы);
- при желании — «ожидают начисления: N бонусов» (опционально).

**Технически (этап 4):**
- новые API: `POST /api/bonus/earn/pending`, `POST /api/bonus/earn/confirm`, `POST /api/bonus/earn/cancel`, `POST /api/bonus/earn/reverse`;
- статусы транзакций: `pending`, `confirmed`, `cancelled`, `reversed`;
- согласование с интегратором Shelter / r_keeper: **на каком событии касса шлёт «отгрузку»** (закрытие заказа, статус в учётной системе и т.д.).

**Важно:** модель закладываем **до** подключения касс — иначе интегратор настроит начисление «сразу при оплате» и переделка будет дороже.

### 2. Бронирование и оплата номеров (как на salanga.ru)

На сайте бронирование: **https://www.salanga.ru/book/** («Подобрать номер»).

**Предложение по этапам:**

#### 2А. Быстрый старт (можно сделать в рамках этапа 2)

| Работа | Детали |
|--------|--------|
| Кнопка на главном экране | **«Забронировать номер»** — рядом с QR, погодой и т.д. |
| Открытие | WebView или браузер → `https://www.salanga.ru/book/` (тот же поток, что на сайте) |
| Авторизация | Пока без связки аккаунта приложения и бронирования на сайте |

**Плюсы:** быстро, без доступа к внутренней системе бронирования.  
**Минусы:** гость «уходит» на сайт; брони в приложении не видны.

**Ориентир:** 30 000 – 60 000 ₽ · **1–2 недели**

#### 2Б. Полная интеграция (отдельный подэтап, после уточнения у заказчика)

| Работа | Детали |
|--------|--------|
| API бронирования | Связь с системой, на которой работает `/book/` (нужны документация / контакт IT salanga.ru) |
| Выбор дат, категорий номеров | Как на сайте: 11 категорий, цены «от … ₽/сутки» |
| Оплата | Эквайринг (Сбер, ЮKassa и т.д. — как на сайте) |
| «Мои бронирования» | Раздел в приложении (на сайте уже есть `/book/reservation_list/`) |
| Push | Напоминания о заезде, статус оплаты (тип `booking` в системе уже заложен) |

**Нужно от заказчика:**
- кто поддерживает модуль бронирования на salanga.ru (1С, TravelLine, собственная разработка?);
- тестовый доступ к API или ЛК;
- те же правила оплаты и отмены, что на сайте.

**Ориентир:** 250 000 – 500 000 ₽ · **6–10 недель** (после получения API)

## Как распределить приложения по этапам (для заказчика)

```
Этап 1   →  Демо APK + Web в браузере                    (уже есть)
Этап 2   →  https + SMS + push
Этап 2А  →  Кнопка «Забронировать номер» → salanga.ru/book (опция)
Этап 2Б  →  Бронирование и оплата внутри приложения       (опция)
Этап 3   →  Google Play и/или App Store
Этап 4   →  Кассы + бонусы по отгрузке (не по оплате)
```

**Web для iPhone** можно не закрывать после этапа 3: часть гостей продолжит пользоваться ссылкой из Safari — это нормально.
