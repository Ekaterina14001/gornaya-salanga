# Приложение № 1  
## к Договору № ДС-165 от 08.10.2026

# Функциональные требования  
## к доработке модуля СПК «Барс.Кассир»  
### Интеграция с бонусной системой курорта «Горная Саланга» по протоколу UDS

---

## 1. Предмет и состав работ

### 1.1. Предмет

Исполнитель выполняет доработку модуля СПК «Барс.Кассир» для взаимодействия с бонусной системой Заказчика через штатную интеграцию по протоколу UDS.  
Далее под **кассовым ПО** понимается модуль СПК «Барс.Кассир».

### 1.2. В состав работ Исполнителя входят

- применение заданных в настройках адреса сервера, авторизации и таймаута запросов;
- запрет обращений к `api.uds.app`, в том числе переключения на него при ошибке;
- реализация возврата по идентификатору исходной бонусной операции (мастер-операции), возвращаемому сервером Заказчика в ответе на успешное проведение покупки (операция Create operation по протоколу UDS);
- сохранение идентификатора мастер-операции, связи с чеком и выполненных возвратов; обработка ответов и ошибок сервера;
- передача Заказчику инструкции по проверке результата операции и безопасному повтору запроса при неопределённом ответе сервера.

---

## 2. Подключение к бонусной системе

**Параметры подключения.** Кассовое ПО должно использовать следующие параметры интеграции UDS.

| Параметр | Требуемое значение |
|----------|-------------------|
| Базовый адрес API | `https://api.salanga.ru/api/partner/v2` |
| Авторизация | HTTP Basic, пара «ИД компании : API-ключ» |
| Таймаут одного запроса | 15 секунд |
| ИД компании и API-ключ | предоставляются Заказчиком для настройки кассы |

Адрес API, реквизиты авторизации и таймаут должны считываться из настроек интеграции. Применение изменённых настроек допускается после повторной инициализации интеграции или перезапуска кассового ПО.

**Направление запросов.** Получение настроек программы лояльности, поиск гостя, предварительный расчёт покупки, проведение покупки (Create operation), получение статуса операции и возврат должны выполняться через настроенный сервер Заказчика. При указанном адресе сервера обращения к `api.uds.app`, в том числе переключение на него при ошибке, не допускаются.

**Инициализация.** При инициализации интеграции касса должна запрашивать настройки программы лояльности. При ошибке авторизации, недоступности сервера или истечении таймаута касса должна сообщать об ошибке и не отображать неподтверждённую бонусную операцию как успешно выполненную.

---

## 3. Требования к проведению покупки

При подключении к серверу Заказчика должна обеспечиваться следующая последовательность:

1. Кассир формирует чек и считывает QR-код гостя из приложения Заказчика.
2. Касса запрашивает данные гостя и предварительный расчёт покупки.
3. Касса отображает полученные от сервера сведения: доступные к списанию бонусы, скидку (лимит лояльности) и количество бонусов к начислению.
4. Кассир применяет бонусы в пределах доступной суммы. Оставшаяся часть покупки оплачивается штатными средствами модуля «СПК Барс.Кассир».
5. При расчёте на кассе в бонусную систему передаётся операция покупки. Сведения об операции печатаются штатными средствами модуля «СПК Барс.Кассир».

Правила начисления, ограничения списания и размер скидки определяются сервером Заказчика. Передача покупки в бонусную систему выполняется при расчёте на кассе. Скидка (лимит лояльности), полученная от сервера, не должна учитываться кассой как сумма списанных бонусов.

При проведении покупки касса передаёт уникальный код операции (поле `nonce` в протоколе UDS и/или номер чека — по согласованной схеме). При повторной отправке запроса с тем же кодом после сбоя связи касса обрабатывает ответ сервера и не фиксирует локально вторую бонусную операцию без подтверждения сервера.

**Сохранение исходной операции.** Для успешно проведённой бонусной покупки касса должна сохранять **идентификатор транзакции внешней системы лояльности** (мастер-операции), возвращаемый сервером Заказчика в ответе на успешную операцию Create operation, а также связь с исходным чеком. Должны сохраняться данные кассы, позволяющие определить возвращаемую позицию и относящиеся к ней суммы. Эти данные должны быть доступны для последующих возвратов, в том числе после перезапуска кассового ПО.

---

## 4. Требования к возврату по исходной бонусной операции

**Модель возврата.** В протоколе UDS при возврате состав корзины (перечень позиций) на сервер лояльности не передаётся. Для бонусной системы значимы **идентификатор исходной (мастер-) операции** и **сумма возврата**. Отдельные понятия «полный» и «частичный» возврат на уровне API не используются. По одной мастер-операции допускается **несколько операций возврата** (в том числе при последовательном возврате отдельных позиций чека штатными средствами кассы). Суммарный объём успешно проведённых возвратов по мастер-операции не должен превышать объём исходной бонусной операции; контроль выполняет сервер Заказчика.

**Идентификатор исходной операции.** При оформлении возврата на кассе касса должна определять исходный чек и связанную с ним мастер-операцию и передавать серверу Заказчика **идентификатор транзакции**, полученный при успешном проведении покупки (Create operation). Повторное предъявление QR-кода гостя не требуется.

**Сценарий возврата.** Кассир оформляет возврат одной или нескольких позиций чека штатными средствами модуля «СПК Барс.Кассир». Касса должна автоматически передавать на сервер Заказчика запрос возврата с указанием идентификатора исходной мастер-операции и суммы, соответствующей возвращаемой кассовой операции (включая отмену начисления и восстановление списанных бонусов — по правилам сервера), и обрабатывать ответ сервера.

**Расчёт суммы возврата.** Передаваемая сумма должна соответствовать возвращаемой позиции (или совокупности позиций) текущей кассовой операции возврата, данным исходной покупки и ответам сервера; должны учитываться применённые скидки и бонусная оплата. Скидка (лимит лояльности) не должна учитываться кассой как сумма списанных бонусов.

**Учёт возвращённых позиций на кассе.** При последовательных возвратах позиций одного чека касса должна учитывать ранее успешно выполненные кассовые и бонусные возвраты. Повторный возврат уже возвращённой позиции не допускается.

**Возврат без списания бонусов по позиции.** Если по возвращаемой позиции начислялись бонусы, но списания бонусов не было, касса должна передавать запрос возврата для отмены начисления по этой позиции. Нулевая сумма списания не должна приводить к пропуску бонусного возврата.

**Денежная и бонусная части.** Возврат денежных средств выполняется штатными средствами модуля «СПК Барс.Кассир». Списанные бонусы восстанавливаются на бонусном счёте через взаимодействие с сервером и не подменяются выдачей денежных средств.

**Подтверждение и сохранение результата.** Бонусный возврат считается успешным только при подтверждении сервером Заказчика. Касса должна сохранять связь каждого выполненного возврата с исходной мастер-операцией и с соответствующей кассовой операцией (позицией). Повторное выполнение уже подтверждённого возврата не должно повторно изменять бонусный счёт на стороне кассового ПО без нового подтверждения сервера.

## 5. Обработка ошибок

**Ошибка возврата.** При отказе сервера, сетевой ошибке или истечении таймаута касса должна выводить сообщение о том, что бонусный возврат не подтверждён. Отсутствие ответа не должно интерпретироваться как успешное выполнение или как достоверный отказ сервера от выполнения операции.

**Неопределённый результат.** Если запрос мог быть выполнен сервером, но подтверждение не получено, повторная отправка допускается только после установления результата предыдущего запроса. Проверка выполняется по данным кассы и ответам сервера (в том числе запрос статуса операции по протоколу UDS). Порядок проверки и безопасного повторного выполнения должен быть описан в передаваемой Исполнителем инструкции. Автоматическая фоновая очередь повторных запросов не требуется.

**Отсутствие исходной операции.** При отсутствии сохранённого идентификатора покупки либо при ответе сервера об отсутствии исходной операции касса должна сообщать об ошибке и не выполнять возврат по произвольно выбранной бонусной операции.
